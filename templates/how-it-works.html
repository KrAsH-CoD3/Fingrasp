01The User Journey

Fingrasp collects device fingerprints through a secure, multi-stage automated process. Here is the full flow:

1

Land & Detect

When you visit, the system immediately begins identifying your platform (iPhone, Android, Mac, etc.) using high-entropy client hints and hardware signals.

2

Platform Lock

Once identified, the platform field is locked to prevent spoofing. This ensure the data we collect matches the actual operating environment.

3

Anti-Bot Verification

We use a combination of Cloudflare Turnstile, hidden honeypots, and behavioral analysis to verify you are a human. This stage protects the research database from bot noise.

4

Select Model

You select or enter your device model. For hardware-constrained platforms like iOS, we provide a pre-filtered list based on your specific screen and hardware profile.

5

Collection & Submit

The system collects the full signal breakdown, generates a SHA-256 composite hash, and submits the validated record via a secure session tunnel.

02Device Detection

Before the submission form appears, Fingrasp runs a multi-signal detection cascade to identify your device platform. This happens entirely in your browser.

Why detect first?
By identifying the platform before rendering the form, we eliminate "layout shift" — where the form initially shows all options and then suddenly locks down. This creates a smoother, more trustworthy user experience.

Signal Priority

The system checks these signals in order, using the first definitive match:

Priority Signal Source Reliability
1 High Entropy Client Hints (UA-CH) Highest
2 User Agent Data (UA-CH API) High
3 navigator.platform Medium
4 User-Agent string parsing Lower

Platform-Specific Behavior

iPhone

Detected via Client Hints or User-Agent. Screen dimensions and DPR are used to determine which exact models share your hardware profile. Only those models appear in the dropdown.

iPad

Modern iPads report as "MacIntel" in navigator.platform. Fingrasp uses touch point detection (maxTouchPoints > 0) to correctly identify iPadOS devices, then filters models by screen size.

Android

Platform is locked to "Android" automatically. Since there are 35,000+ Android models, a free-text input is shown. The backend verifies the model against an official Google device database.

Desktop

Mac, Windows, and Linux are detected via Client Hints and User-Agent. GPU renderer strings from WebGL are used to identify specific hardware like Apple Silicon Macs or dedicated GPUs.

03Fingerprint Collection

Once validated, the system collects a comprehensive set of browser and hardware signals using the MixVisit fingerprinting library. Here is what gets collected:

Browser Metadata

User-Agent, language, timezone, Do-Not-Track flag, cookie support, installed plugins

Hardware Hints

CPU cores, device memory, screen resolution, color depth, device pixel ratio

Graphics Fingerprint

WebGL renderer, vendor, canvas hash — unique patterns generated by your GPU hardware

Audio Fingerprint

AudioContext oscillator output hash — a unique signature from your audio processing pipeline

Font Detection

Installed system fonts detected through rendering measurement — no filesystem access required

Network Indicators

Connection type, IP address (captured server-side and anonymized before storage)

All these signals are combined and hashed into a single SHA-256 composite fingerprint. This hash serves as a unique identifier for your device configuration — without storing any personally identifiable information.

04Model Validation

Fingrasp does not blindly trust the device model you provide. The backend runs a multi-layer validation process to ensure what is saved in the database matches your actual hardware.

Layer 1

Platform Consistency Check

Compares the platform implied by your model selection (e.g., "iPhone" implies iOS) against the platform detected from your fingerprint's hardware signals. If they do not match — for example, you claim "iPhone" but your signals indicate "Windows" — the system overrides your input completely.

Layer 2

Android Memory & Store Lookup

For Android devices, the backend extracts the hidden model code from the fingerprint and looks it up in a 35,000+ device database. Crucially: if the fingerprint signal is missing but the user types a model name manually, the system still validates that text against our device store to standardize it (e.g., "S24" → "Samsung Galaxy S24").

Layer 3

iOS Screen-Size Verification

For iPhone and iPad devices, the backend re-calculates your screen dimensions and DPR from the raw fingerprint data. It then checks if the model you selected is in the list of valid models for that hardware profile. If not, both your selection and the hardware truth are recorded: Your Choice (Detected Hardware).

Layer 4

Hardware Ground-Truth Tagging

For platforms that allow manual text input (like Desktop or Unknown Androids), if the user's input cannot be verified as a known device, Fingrasp automatically appends the detected hardware profile. An entry submitted as asdfghjkl on a Windows machine is saved as asdfghjkl (Windows PC), ensuring data integrity.

The result: it is effectively impossible to store a fake device model in the database. The system will always either correct it or flag it for review.

05Security Architecture

Fingrasp is designed with defense-in-depth. Every interaction passes through multiple security layers before any data touches our research database.

Layered Anti-Bot Filtering

We employ a 3-phase check: Cloudflare Turnstile for cryptographic proof of humanity, hidden honeypots to catch headless bots, and interaction scoring to verify legitimate behavioral patterns before granting session access.

Secure Tunnel Handshake

Upon passing anti-bot checks, the backend issues a single-use session token. All submissions must traverse this "secure tunnel," and tokens are immediately invalidated upon use to prevent replay attacks.

Hardened Rate Limiting

All endpoints are governed by SlowAPI (10 req/min for API, 30 req/min for frontend). Static assets are also dynamically rate-limited to preserve server resources and mitigate scraping.

Nonce-Based Content Security

Our CSP strictly forbids inline scripts and styles. Every resource is verified via dynamically generated nonces, ensuring that only our authorized codebase can execute in your browser.

Pydantic Validation & Sanitization

Data payloads are strictly validated against production schemas. We enforce type checking, max-length constraints, and NoSQL operator sanitization to prevent injection vulnerabilities.

06Data Lifecycle

Understanding what happens to your data after submission is just as important as understanding what we collect. Here is the complete lifecycle:

Collection

Your browser signals are gathered client-side by MixVisit and transmitted over HTTPS.

IP Anonymization

Your IP address is anonymized before storage. The last octet (IPv4) or last 80 bits (IPv6) are zeroed out, making it impossible to trace back to you.

Model Validation

Your device model is cross-referenced against hardware signals and corrected if inconsistencies are found.

Persistent Storage

The validated fingerprint document is stored in an encrypted MongoDB database with restricted access controls.

Research Analysis

Fingerprints are analyzed in aggregate — measuring entropy, collision rates, and signal stability across devices and browsers.

Anonymization & Archival

Once the research lifecycle is complete, raw records are irreversibly transformed into statistical models with no link to individual hardware configurations.
